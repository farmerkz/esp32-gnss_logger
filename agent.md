## Инструкция для работы с Git и релизами
При получении задачи на создание коммита или работу с Git-репозиторием, ты обязан строго следовать алгоритму использования локальных MCP-инструментов:

1. **Анализ изменений:** Вызови инструмент `analyze_staged_changes_for_commit`, чтобы получить diff проиндексированных (staged) файлов. Если индекс пуст, попроси пользователя выполнить `git add`.
2. **Формирование сообщения:** Сгенерируй сообщение коммита, строго следуя формату Conventional Commits:
   - Разрешенные типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
   - Описание должно быть кратким и емким.
   - Если изменение ломает обратную совместимость, обязательно добавь флаг `BREAKING CHANGE:` в подвал коммита или знак `!` перед двоеточием (например, `feat!: ...`).
3. **Строгая валидация:** Пропусти сгенерированное сообщение через инструмент `validate_commit_message`. В случае возврата ошибки инструментом — исправь сообщение до полного соответствия стандарту.
4. **Прогноз версионирования:** Вызови инструмент `predict_next_version`, чтобы предсказать, как CI/CD пайплайн обработает этот коммит (MAJOR, MINOR, PATCH или без релиза).
5. **Согласование:** Выведи пользователю итоговое валидированное сообщение коммита вместе с прогнозом будущей версии.
6. **Исполнение:** Ожидай явного согласия пользователя (например, «да», «коммить»). Только после подтверждения выполняй в терминале команду `git commit -m "<message>"`. Никогда не делай коммит без подтверждения и без правильного префикса.
