# Инструкция для агента Antigravity по проекту ESP32 GNSS Logger & Wardriving

Настоящий документ содержит спецификацию архитектуры, структуру модулей и требования к программному обеспечению **ESP32 GNSS Logger & Wardriving**.

---

## 1. Назначение системы

Программное обеспечение предназначенное для микроконтроллера ESP32, выполняющее функции автономного сбора геопространственных данных (GNSS трекинг) и сканирования параметров Wi-Fi сетей (Wardriving) с сохранением логов на SD-карту и последующей отгрузкой на удаленный FTP сервер.

ПО разработано строго на базе **ESP-IDF v6.x (Native C / CMake)** и операционной системы **FreeRTOS**.

## 3. Требования к реализации и стандарты разработки

### 3.1 Запреты и ограничения
- **Строгий отказ от библиотеки Arduino и PlatformIO**: проект использует **исключительно нативные драйверы ESP-IDF** (`driver/uart.h`, `driver/sdspi_host.h`, `esp_wifi`, `cJSON`, `esp_ota_ops`, `nvs_flash`, `driver/ledc.h`).
- **Запрет на использование RGB светодиодов**: световая индикация не используется. Сигнализация выполняется **только со звуковым оповещением (Buzzer)** на пине GPIO 25.
- **Язык комментариев**: Все комментарии к коду, документы и спецификации **должны быть выполнены на русском языке**.
- **Обязательная компиляция и отладка**: При внесении любых изменений в код необходимо в обязательном порядке проверять внесенные изменения путем компиляции. В случае обнаружения ошибок проводить отладку до достижения успешной сборки.
- **Обязательная актуализация документации**: При внесении любых изменений в код, структуру модулей, API или параметры конфигурации после успешной компиляции и отладки агент обязан произвести актуализацию сопутствующей документации проекта (`README.md`, `CONFIG.md` и спецификаций).
- **Регламент управления Git-репозиторием**: Фиксация изменений в локальном репозитории (`git commit`), а также отправка в удаленный репозиторий (`git push`) производятся **строго по явному запросу пользователя**.
- **Регламент прошивки устройств**:
  - Агент **никогда не загружает прошивку самостоятельно**. Загрузка выполняется **строго по явному запросу пользователя**.
  - Загрузка прошивки производится **только через UART**.
  - Если порт подключения не был указан пользователем, агент обязан определить его самостоятельно в системе (например, поиск `/dev/tty.usbserial*`, `/dev/ttyUSB*` и т.п.).
  - Загружается **полная прошивка**, включающая в обязательном порядке таблицу разделов (`partitions.csv`), загрузчик (`bootloader`) и приложение.
- **Безопасность OTA-обновлений и обратная совместимость**:
  - При добавлении нового функционала, параметров конфигурации, изменении структур NVS или VFS необходимо выполнять обязательный анализ на предмет риска возникновения фатальной ошибки (Fatal Error / Crash loop) при старте нового образа прошивки, загруженного поверх предыдущей версии по OTA.
  - Если возникновение фатальной ошибки при прямом обновлении возможно, агент обязан предложить пользователю вариант поэтапного обновления (миграции) через промежуточные версии (не более двух промежуточных прошивок).

### 3.2 Автоопределение и настройка UART GNSS модуля (`app_gnss.c`)
- При старте состояние GNSS модуля и его скорость не гарантируются — выполняется полная детерминированная инициализация при каждом старте.
- Функция `app_gnss_init()` обязана выполнить поочередную проверку скоростей из списка `[115200, 9600, 38400, 57600, 19200]`.
- Пробирование производит отслеживание как **UBX ответов** (на запрос `UBX-MON-VER`), так и **NMEA строк** (символ `$`), что позволяет определять скорость модулей в заводском режиме NMEA. Функция `app_gnss_probe_baud()` возвращает флаг `out_ubx_detected`, отличающий UBX-ответ от NMEA.
- **`UBX-CFG-PRT` отправляется всегда**: при любой скорости или NMEA-режиме, чтобы гарантировать 115200 бод и вывод только UBX (`outProtoMask = 0x0001`).
- После установки UBX-режима обязательно следует активировать навигационные сообщения через **`UBX-CFG-MSG`**: явное включение `NAV-PVT` (0x01/0x07) и `NAV-DOP` (0x01/0x04).
- Перед запуском задачи приёма обязательно вызывается `ubx_parser_init()` — исключает грязное состояние FSM после зондирования.

### 3.3 Безопасность записи GPX и усечение поврежденных тегов (`app_gpx.c`)
- Инкрементальная запись точек `<trkpt>` должна сопровождаться моментальным вызовом `fflush()`.
- При закрытии файла или очистке рабочих папок вызывается `app_gpx_repair_and_close()`:
  - Проводится поиск с конца файла последнего валидного завершенного тега `</trkpt>`.
  - В случае выявления обрыва тега из-за отключения питания файл усекается до корректной границы (`ftruncate`), после чего дописываются закрывающие теги `</trkseg></trk></gpx>`.

### 3.4 Изоляция активных файлов и отгрузки FTP (`app_wigle.c`, `app_ftp.c`)
- Активная запись GPX треков и Wigle CSV производится **строго** в папки `/sdcard/gps.wk` и `/sdcard/wifi.wk`.
- Перенос файлов из `.wk` в папки готовности `.rd` выполняется только при их корректном закрытии и ротации.
- Задача `app_ftp` производит чтение и отправку файлов **исключительно** из каталогов `.rd`. Это гарантирует отсутствие гонок данных и повреждения открытых файлов.

### 3.5 Синхронизация доступа к SD-карте
- Все операционные вызовы VFS файловой системы (`fopen`, `fwrite`, `fread`, `fclose`, `rename`, `unlink`, `opendir`, `stat`) должны выполняться под защитой глобального мьютекса `g_sd_mutex`.

### 3.6 Форматы файлов
- **GPX трек**: стандартный формат версии 1.0 со структурами `<trkpt lat="..." lon="...">...` с указанием времени UTC, высоты, скорости, курса, числа спутников, PDOP, hMSL, hAcc, vAcc.
- **Wigle CSV**: стандарт версии 1.4 с первой строкой заголовка `WigleWifi-1.4...`, второй строкой параметров `MAC,SSID,AuthMode...` и строками записей BSSID, SSID, AuthMode, FirstSeen, Channel, RSSI, Lat, Lon, Alt, Acc, Type.

### 3.7 Тестирование парсера UBX
- В корне проекта расположен автономный тестовый файл `test_ubx_parser.c` (12 TC).
- Компилируется и запускается `gcc` без ESP-IDF и без железа на хост-машине.
- При любых изменениях в `ubx_parser.c` или `ubx_parser.h` обязательно запускать тесты и убеждаться, что все 12 TC проходят.

## 6. Обязательные стандартные сценарии (Workflows)

### 6.1. Сценарий A: Создание коммита (Commit Pipeline)

При создании коммита агент **ОБЯЗАН** строго соблюдать следующий порядок вызова инструментов:

1. **Шаг 1. Анализ staged-изменений**:
   * Вызовите инструмент `analyze_staged_changes_for_commit(workdir=".")`.
   * Если инструмент вернул `❌ Ошибка: Нет проиндексированных файлов`, сначала выполните `git add` или попросите пользователя проиндексировать файлы.
   * Если в ответе содержится `[ДИФФ ОБРЕЗАН ИЗ-ЗА РАЗМЕРА]`, учтите, что показана только первая часть диффа. Предложите пользователю разбить изменения на отдельные коммиты (`git add -p`).

2. **Шаг 2. Формирование сообщения**:
   * Сформируйте текст сообщения коммита строго по спецификации **Conventional Commits**:
     * `feat`: новый функционал
     * `fix`: исправление ошибки
     * `docs`: изменение документации
     * `style`: форматирование, пробелы
     * `refactor`: рефакторинг без изменения внешней логики
     * `perf`: оптимизация производительности
     * `test`: добавление или исправление тестов
     * `build` / `ci`: сборка или CI/CD
     * `chore`: прочие служебные задачи
   * Описание должно быть в повелительном наклонении (например, `feat(auth): добавить поддержку OAuth2`).

3. **Шаг 3. Обязательная валидация сообщения**:
   * Перед выполнением команды `git commit` **всегда** вызовите `validate_commit_message(message=generated_msg)`.
   * Если результат содержит `❌ Ошибка валидации`, скорректируйте текст коммита до получения `✅ Успешно`.

4. **Шаг 4. Финализация**:
   * Выведите пользователю предложенный текст коммита и выполните коммит с его согласия.

5. **Шаг 5. Прогнозирование версии после коммита**:
   * После выполнения коммита типов `feat` или `fix` агент **ОБЯЗАН** сразу вызвать `predict_next_version(workdir=".")`.
   * Сообщить пользователю предсказанную новую версию и спросить, требуется ли актуализировать `version.txt` и пересобрать прошивку.

---

### 6.2. Сценарий B: Прогнозирование версии релиза

При планировании релиза, тегировании или формировании списка изменений (Changelog):

1. Вызовите инструмент `predict_next_version(workdir=".")`.
2. Если ответ содержит предсказанную версию `🚀 Semantic Release предсказывает выпуск версии: X.Y.Z`, сообщите ее пользователю.
3. Если получен ответ `ℹ️ Текущие непримененные изменения не требуют повышения версии`, проинформируйте пользователя, что коммиты содержат только типажи без повышения версии (например, `chore` или `docs` при стандартных настройках).

---

### 6.3. Сценарий C: Стратегия ветвления и работа с GitHub

1. **Правила ветвления:**
   * Все новые ветки для задач (`feat`, `fix`, `chore`) создаются **строго от ветки `dev`**.
   * Перед созданием ветки убедитесь, что находитесь в `dev` и она синхронизирована: `git checkout dev && git pull origin dev`.
   * Имена веток формируются по шаблону: `<тип>/<краткое-описание>` (например, `feat/add-sensor`, `fix/memory-leak`).

2. **Использование GitHub MCP Server:**
   * Для работы с GitHub (Pull Requests, CI/CD, Issues) используйте инструменты `github-mcp-server` вместо консольных утилит (например, `gh`).
   * При интеграции задачи создавайте Pull Request из рабочей ветки в ветку `dev` через MCP.
   * Запрашивайте статус проверок CI/CD (GitHub Actions) через MCP сервер после создания PR или отправки коммитов, чтобы информировать пользователя о результатах сборки.

## 7. Запреты и предостережения для агентов

* ❌ **Запрещено вызывать `git commit` без предварительной валидации**: Никогда не выполняйте `git commit -m ...` без успешного ответа от `validate_commit_message`.
* ❌ **Запрещено игнорировать статус staged-файлов**: Запрещено предполагать состав коммита по памяти; всегда используйте `analyze_staged_changes_for_commit`.
* ❌ **Запрещено умалчивать об обрезанном диффе**: Если дифф был обрезан из-за размера, агент должен явно сообщить об этом пользователю.
* 🔒 **Неприкосновенность кода при обновлении документации**: При актуализации инструкций или документации функциональный исходный код проекта (`C`-файлы) не подлежит изменению, если пользователя об этом не просили.
