# ESP32 GNSS Logger & Wardriving System

Программное обеспечение для автономного высоконадежного логирования треков навигации в формате **GPX** и географического сканирования сетей Wi-Fi в формате **Wigle CSV v1.4** с последующей автоматической загрузкой сформированных файлов на **FTP сервер**. Разработано на базе фреймворка **ESP-IDF v6.x (Native C / CMake)** с использованием операционной системы реального времени **FreeRTOS**.

## 🚀 Назначение и возможности

Устройство предназначено для автономной записи маршрутов движения, сбора данных о беспроводных сетях Wi-Fi и выгрузки накопленных логов на удаленный FTP сервер при появлении заданной точки доступа.

### Ключевые функции:
- **Автоматическое автоопределение скорости UART GNSS модуля**: сканирование базовых скоростей (`115200`, `9600`, `38400`, `57600`, `19200` бод) при включении питания. Детектирование выполняется как по **UBX бинарным пакетам**, так и по **NMEA-предложениям** (символ `$`) — поддерживаются модули в заводском NMEA-режиме. При обнаружении скорости, отличной от 115200, автоматически выполняется переключение командой `UBX-CFG-PRT` с верификацией.
- **Высоконадежное GPX логирование**: непрерывная инкрементальная запись координат, скорости, курса, высоты, параметров точности (PDOP, HDOP, hAcc, vAcc) и числа спутников.
- **Отказоустойчивость при аварийном отключении питания**: специализированный механизм анализа целостности структуры GPX файлов с автоматическим усечением битых обрывков записей при ротации перед закрытием.
- **Сканирование Wi-Fi эфира (Wardriving)**: регулярный поиск открытых и защищенных точек доступа с записью BSSID, SSID, типа шифрования, уровня сигнала (RSSI), канала и точных координат фиксации в стандарте **Wigle CSV v1.4**.
- **Безопасная и изолированная FTP отгрузка**: гарантированное разделение открытых на запись файлов и файлов, подготовленных к передаче, что исключает повреждение данных во время сетевых операций.
- **Встроенный Web-интерфейс и веб-диагностика**: просмотр параметров системы в реальном времени, отображение причины последней перезагрузки и времени работы (Uptime), фиксация даты и времени сборки прошивки (`__DATE__ __TIME__`), интерактивный чек-лист оборудования (NVS, Wi-Fi, SD, GNSS), кнопка перезагрузки устройства и просмотр логов. Встроенный редактор конфигурации читает параметры напрямую из файла `config.json` на SD-карте, обеспечивая точное отображение физически записанных на диск настроек.
- **Фоновое логирование (Syslog) на SD-карту**: все системные сообщения перехватываются в кольцевой буфер и каждые 5 секунд сбрасываются на карту памяти в файл `/sdcard/syslog.txt`. При превышении размера в **10 МБ** выполняется автоматическая ротация с сохранением резервной копии `syslog.bak.txt`.
- **Автономное и сетевое OTA обновление прошивки (Rollback)**: поддержка обновления через SD-карту (`/sdcard/firmware.bin`) или через Web-интерфейс (загрузка бинарника с **произвольным именем** и расширением `*.bin`). Валидация заголовка (Magic byte `0xE7`), SHA-256 и автоматический откат (`Rollback`) на предыдущую версию при панике при первом старте.
- **Двухуровневое хранение настроек**: чтение конфигурации с SD-карты с автоматическим резервированием и восстановлением из энергонезависимой памяти **NVS Flash**.

## 🛠 Собственная библиотека парсинга UBX

Для взаимодействия с навигационными модулями u-blox разработан легкий специализированный компонент `ubx_parser`.

### Принцип работы парсера:
- **Конечный автомат (FSM)** обработчика байтов:
  `IDLE` -> `SYNC2` (`0x62`) -> `CLASS` -> `ID` -> `LEN_LSB` -> `LEN_MSB` -> `PAYLOAD` -> `CK_A` -> `CK_B`.
- **Нулевой динамический память в рантайме**: все данные обрабатываются во внешнем статическом контексте `ubx_parser_t`.
- **Поддерживаемые типы входящих сообщений**:
  - `UBX-NAV-PVT` (Class `0x01`, ID `0x07`): координатно-временные решения и точностные характеристики.
  - `UBX-NAV-DOP` (Class `0x01`, ID `0x04`): значения факторов понижения точности (pDOP, hDOP, vDOP, gDOP).
  - `UBX-ACK-ACK` / `UBX-ACK-NAK` (Class `0x05`): подтверждения выполнения команд.
  - `UBX-MON-VER` (Class `0x0A`, ID `0x04`): отклик версии навигационного модуля.
- **Конструкторы конфигурационных команд**:
  - `ubx_build_cfg_prt_baud()`: изменение скорости UART1, переключение вывода в режим UBX-only (`outProtoMask = 0x0001`).
  - `ubx_build_cfg_msg()`: включение/выключение вывода конкретного UBX-сообщения (3-байтовая форма CFG-MSG SET).
  - `ubx_build_cfg_nav5()`: установка ограничений масок PDOP и Position Accuracy.
  - `ubx_build_cfg_rate()`: настройка навигационной частоты (1 Гц).
  - `ubx_build_mon_ver_poll()`: запрос версии прошивки.

## 🔌 Требования к аппаратным ресурсам

| Модуль | Пин ESP32 | Описание / Протокол |
| :--- | :--- | :--- |
| **GNSS TX** | GPIO 16 | Прием данных от GNSS модуля (RX ESP32 <- TX GNSS) |
| **GNSS RX** | GPIO 17 | Передача команд в GNSS модуль (TX ESP32 -> RX GNSS) |
| **SD CS** | GPIO 5 | Выбор ведомого устройства SPI |
| **SD MOSI** | GPIO 23 | Линия данных Master Out Slave In |
| **SD MISO** | GPIO 19 | Линия данных Master In Slave Out |
| **SD CLK** | GPIO 18 | Тактовая линия SPI |
| **Buzzer** | GPIO 25 | Активная пищалка (ШИМ управление через LEDC) |

### ⚠️ Аппаратные требования для SPI SD-карты

- **Pull-up резистор на MISO (GPIO 19)**: линия MISO **обязательно** должна иметь подтяжку к VCC (рекомендуется 10 кОм). Без неё возникает `ESP_ERR_TIMEOUT` при чтении SCR регистра SD-карты (`sdmmc_check_scr`). Программный pull-up через `gpio_set_pull_mode()` включён в коде, однако для надёжности рекомендуется установить внешний резистор.
- **Частота SPI шины**: установлена **4 МГц** (`max_freq_khz = 4000`) для обеспечения стабильной работы на коротких соединениях без дополнительной экранировки.

## ⚙ Конфигурация устройства (`config.json` & NVS)

При старте устройство ищет конфигурационный файл `/sdcard/config.json`. В случае его отсутствия параметры восстанавливаются из `NVS Flash`.

Подробное руководство со спецификацией всех доступных ключей, типов и значений по умолчанию см. в документе [CONFIG.md](file:///Users/andreyzolotnitskiy/Documents/github/esp32-gnss_logger/CONFIG.md).

### Пример файла `/sdcard/config.json`:

```json
{
  "ssid": "MyWiFiAP",
  "wifipasswd": "MySecretPassword",
  "ftpaddress": "192.168.1.100",
  "ftpuser": "ftpuser",
  "ftppassword": "ftppasswd",
  "ftpport": 21,
  "filesize": 1000000,
  "gpssend": true,
  "wifisend": true,
  "ftpbeep": true,
  "moduleid": "01",
  "pdopmask": 0,
  "paccmask": 0,
  "min_track_size": 1000
}
```

### Описание параметров:
- `ssid` — Имя точки доступа Wi-Fi для выполнения FTP загрузки.
- `wifipasswd` — Пароль точки доступа Wi-Fi.
- `ftpaddress` — IP-адрес FTP сервера.
- `ftpuser` — Имя пользователя FTP.
- `ftppassword` — Пароль пользователя FTP. Максимальная длина — 31 символ. По умолчанию `"ftppasswd"`.
- `ftpport` — Порт подключения FTP (по умолчанию `21`).
- `filesize` — Пороговый размер Wigle CSV файла в байтах для ротации (по умолчанию `1000000` (1 МБ)). Ограничение применяется только к файлам с данными по Wi-Fi. Файлы с треками GPX ограничиваются размером в 50 МБ, а системный лог — 10 МБ.
- `gpssend` — Разрешение отправки файлов GPX треков (`true`/`false`).
- `wifisend` — Разрешение отправки Wigle CSV файлов (`true`/`false`).
- `ftpbeep` — Воспроизведение звукового сигнала после завершения отправки (`true`/`false`).
- `moduleid` — Идентификатор устройства для имен файлов (по умолчанию `"00"`). При отправке на FTP добавляется перед расширением (например, `gps-2026-07-27_070609-00.gpx`).
- `pdopmask` — Пороговая маска PDOP (0 — без изменений).
- `paccmask` — Пороговая маска точности Position Accuracy в метрах (0 — без изменений).
- `timezone` — Смещение системного времени микроконтроллера в часах относительно UTC (по умолчанию `5`, т.е. UTC+5).
- `min_track_size` — Минимальный размер GPX/CSV файла в байтах для переноса в `.rd` при старте. Файлы меньше указанного размера удаляются (по умолчанию `1000` байт).

## 🛡 Алгоритмы работы и защита данных

### 1. Потоковая запись и защита от отключения питания в GPX
Запись каждой точки выполняется с моментальным сбросом буферов `fflush()`. При старте или завершении файла перед его переносом в готовность вызывается функция `app_gpx_repair_and_close()`:
- Файл сканируется с конца на предмет наличия полного тега `</trkpt>`.
- Если файл обрывается на некорректно записанной точке из-за отключения питания, поток усекается (`ftruncate`) до границы последней целой точки.
- В конец корректных данных дописываются завершающие теги `</trkseg></trk></gpx>`.

### 2. Алгоритм инициализации и конфигурации GNSS модуля

Модуль `app_gnss` реализует полную детерминированную инициализацию при каждом старте, независимо от начального состояния подключённого GNSS-приёмника:

1. **Автоопределение скорости**: пробуются скорости `[115200, 9600, 38400, 57600, 19200]` бод. Детектируются как UBX-ответы, так и NMEA-строки (символ `$`).
2. **Переключение скорости и режима вывода через `UBX-CFG-PRT`**:
   - Если обнаруженная скорость отличается от 115200 — отправляется `CFG-PRT(115200)`, ESP32 переключается на 115200, связь верифицируется.
   - Если скорость уже 115200, но модуль ответил NMEA (не UBX) — `CFG-PRT` отправляется повторно для перевода в режим `outProtoMask = UBX only`. Связь верифицируется.
3. **Активация навигационных сообщений через `UBX-CFG-MSG`**: явное включение `NAV-PVT` и `NAV-DOP` на UART1 (частота 1 раз в навигационную эпоху).
4. **Конфигурация параметров навигации**: отправка `CFG-NAV5` (маски PDOP/PACC из конфига) при ненулевых значениях.
5. **Настройка частоты**: `CFG-RATE` — 1 Гц (1000 мс).
6. **Сброс FSM парсера** перед запуском задачи приёма — исключает «грязное» начальное состояние после зондирования.
7. **Запуск задачи `gnss_rx_task`** на ядре 1.

### 3. Логика управления Wi-Fi и FTP отгрузкой

Модуль `app_ftp` управляет подключением к Wi-Fi AP по двум независимым условиям с чётким приоритетом:

**Приоритет 1 — Веб-сервер** (`webserver_enable=true` + заданы логин/пароль):
- Подключение к AP поддерживается **постоянно**, пока выполняются условия активации.
- При потере связи выполняются попытки переподключения с экспоненциальным backoff: первые 3 попытки — раз в 60 сек, далее — раз в 300 сек.
- AP не отключается, пока веб-сервер включён в конфигурации.

**Приоритет 2 — FTP отгрузка** (`gps_send` или `wifi_send`):
- Каждые 30 секунд проверяется наличие файлов в каталогах `.rd`.
- Если файлы есть и **веб-сервер активен**: FTP использует уже установленное соединение без принудительного переподключения. Если AP временно недоступен (backoff активен) — итерация пропускается.
- Если файлы есть и **веб-сервер выключен**: выполняется разовое подключение к AP, затем файлы передаются, после чего AP отключается.
- Активный веб-сервер **не блокирует и не мешает** FTP-отгрузке доступных файлов.

**Защита файлов от конкурентного доступа и совместимость с FTP-серверами**:
Задачи записи GPX и Wigle CSV работают исключительно в каталогах `.wk`. Перенос в `.rd` выполняется атомарно при закрытии файла. Задача `app_ftp` обрабатывает файлы из `.rd` по одному: открывает директорию под мьютексом, читает имя файла, затем передаёт файл по FTP без удержания мьютекса (долгая сетевая операция), и переносит в `.sd` под мьютексом. 
На стороне FTP-сервера используется атомарная загрузка через `.partial` с последующим переименованием (`RNFR`/`RNTO`). Файлы автоматически распределяются по соответствующим целевым папкам на FTP сервере: треки загружаются в каталог `gps.rd/`, а Wi-Fi сканы — в `wifi.rd/`. Клиент поддерживает стандарт RFC 959, включая корректную циклическую сборку многострочных ответов сервера (совместимость с баннерами ProFTPD `220-`), валидацию промежуточных кодов `125`/`150` перед отправкой данных `STOR`, буферизацию пакетов и расширенную диагностику I/O сокетов (с увеличенным пулом до 16 одновременных сокетов).

### 4. Данные DOP (Dilution of Precision)

Модуль `app_gnss` принимает и хранит данные `UBX-NAV-DOP` параллельно с `NAV-PVT`. Полный набор коэффициентов точности (`pDOP`, `hDOP`, `vDOP`, `gDOP`, `nDOP`, `eDOP`) доступен через функцию `app_gnss_get_latest_dop()`. GPX-трек записывает поле `<pdop>` на основе данных **из поля `NAV-PVT.pDOP`** (не из `NAV-DOP`), что обеспечивает синхронизацию pDOP с координатами в одной навигационной эпохе.

## 🔊 Звуковая сигнализация (Buzzer)

Управление звуком осуществляется модулем `app_buzzer` через нативный драйвер `LEDC`.

| Событие | Частотный паттерн | Описание |
| :--- | :--- | :--- |
| **Старт системы** | 1000 Гц (120 мс) -> 1500 Гц (160 мс) | Двойной восходящий тон при успешной инициализации |
| **Ротация файла** | 2000 Гц (20 мс) | Короткий тихий щелчок при смене файла |
| **Успех FTP** | 1000 Гц -> 1250 Гц -> 1500 Гц | Мажорный тройной аккорд завершения передачи |

## 🚀 Сборка и прошивка

### Требования к среде сборки:
- Установленный инструментарий **ESP-IDF v6.x**.

### Шаги сборки:

```bash
# 1. Активация окружения ESP-IDF (в зависимости от вашей установки)
. $IDF_PATH/export.sh

# 2. Установка целевого микроконтроллера
idf.py set-target esp32

# 3. Сборка проекта
idf.py build

# 4. Прошивка и запуск встроенного монитора порта
idf.py -p /dev/ttyUSB0 flash monitor
```

### Запуск автономных тестов парсера UBX:

Файл `test_ubx_parser.c` содержит 12 контрольных тест-кейсов (TC-01..TC-12) для компонента `ubx_parser`.
Компилируется и запускается на хост-машине без ESP-IDF:

```bash
gcc -o test_ubx_parser \
    test_ubx_parser.c \
    components/ubx_parser/ubx_parser.c \
    -I components/ubx_parser/include \
    -Wall -Wextra
./test_ubx_parser
```
